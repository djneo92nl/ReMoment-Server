# Library API

Browse the shared media library and its playlists, keep household favorites, and play albums, artists or playlists on a device. All endpoints are under `/api`, unauthenticated like the rest of the API. Controller: `app/Http/Controllers/Api/LibraryController.php` (browse, favorites) and `Api/DeviceController` (`library/*` playback); playback logic: `app/Domain/Library/LibraryPlayback.php`, shared with the web Album/Artist/Playlist/track play buttons.

## Shapes

**Artwork** — `{ "hash": "<md5 of the cover URL>", "proxy_120": "…", "proxy_320": "…", "colors": ["#…"], "safe_colors": ["#…"] }`, or `null` when the cover is not processed yet (or there is none). URLs are root-relative (`/storage/artwork/…`), never with a host: prefix `artwork_base_url` from `GET /api/info` (a client should also accept an absolute URL and take its path from `/storage/`); `hash` is the same as in the pre-cache list (`GET /api/clients/{api_token}/artwork`) and the SD card export, so a client can use its cached files. `colors` / `safe_colors` are the palette of the full artwork object (same format and meaning: five dominant colours, and those lightened to at least 65% lightness for text on dark backgrounds), read from the cover's artwork cache entry; they are `null` (keys always present) when the entry expired or predates the palette while the proxies still exist, until the cover is processed again. A missing cover is queued for processing at most once an hour per image (`App\Domain\Artwork\LibraryItemArtwork`); requests never wait for a download.

**ArtistItem** — `{ "id": 1, "name": "Muse", "album_count": 4, "artwork": Artwork|null, "favorite": false }`. `artwork` is the cover of the artist's most played album with an image.

**AlbumItem** — `{ "id": 12, "name": "Absolution", "artist_name": "Muse", "year": 2003|null, "artwork": Artwork|null, "favorite": false }`.

**PlaylistItem** — `{ "id": 3, "name": "Discover Weekly", "track_count": 42, "owner": "Spotify"|null, "last_played_at": ISO8601|null, "artwork": Artwork|null }`; `GET /api/library/playlists` adds `"library"`, `"external"`, `"local_track_count"` and `"local_coverage"` (see [Playlists of another library, played locally](#playlists-of-another-library-played-locally)). `last_played_at` is when it was last started from the server (null if never). The list's `library` is the library the playlist belongs to (`spotify` for a Spotify playlist, `null` for local and smart playlists, which can mix libraries; `GET /api/library/playlists/{id}` has `sources`). `owner` is the Spotify owner's display name (`null` for local and smart playlists). Smart playlists (rule-based, refreshed daily; see `docs/architecture/smart-playlists.md`) appear in the playlist list like any other and play the same way. `artwork` is a cover generated by the server (see [Playlist artwork](#playlist-artwork)).

`year` comes from `albums.released_at`. Artists, albums and tracks are the library's rows, **one per artist/album/track whatever the source**: a DLNA scan, the Spotify import and plays resolve to the same record by a normalized name (case, "The ", diacritics, punctuation, "feat." credits and edition suffixes like "(Remastered 2011)" or "- Deluxe Edition" ignored; "(Live)" and the like kept apart). A track can then have both a DLNA URL and a Spotify URI. See `docs/architecture/library-identity.md`.

### Merged records and stale ids

Duplicates from before that are merged by an admin running `php artisan library:merge-duplicates`: the oldest record keeps its id, the others' **ids disappear**. A client holding such an id gets `404` from `GET /api/library/artists/{id}`, `GET /api/library/albums/{id}` and the `PUT …/favorite` endpoints, and a `422` validation error for `album_id`/`artist_id`/`track_id`/`start_track_id` in the play requests. Treat either as "gone": drop the cached id and re-read the list (`/api/library/artists`, `recent`, `favorites`), where the merged record appears with its surviving id. Favorites survive a merge (the earliest `favorited_at` is kept). Artwork `hash`es are per cover URL, so cached covers stay valid.

## Browse

### `GET /api/library/artists?cursor=&letter=&sort=`

`{ "data": [ ArtistItem, … ], "next_cursor": "…"|null }` — artists with at least one album, alphabetical (case-insensitive, a leading "The " ignored), 50 per page. Pass `next_cursor` back as `cursor` until it is `null`. The cursor is opaque; an invalid one returns Laravel's `422` validation error. `sort` is `name` (default) or `plays` (most played first; any other value is a `422`). Plays of an artist are the plays of the tracks on its albums that are visible in the requested scope (`scope=dlna` counts only plays of tracks available from DLNA, and the client's hidden sources apply). Artists without plays come last; ties fall back to name ("The " ignored) then id, so paging with the cursor is stable. `letter` has no effect with `sort=plays`.

### `GET /api/library/albums?cursor=&sort=&letter=`

`{ "data": [ AlbumItem, … ], "next_cursor": "…"|null }` — every album with at least one visible track, 60 per page, paged like artists (opaque `cursor`). `sort` is `name` (default, case-insensitive), `artist` (artist name with "The " ignored, then album name), `year` (newest first, unknown year last), `added` (newest in the library first) or `plays` (most played first); any other value is a `422`. Ties fall back to the album id, so paging is stable. `letter` jumps to a letter in the active sort key (see [Jumping to a letter](#jumping-to-a-letter)) and has no effect with `year`, `added` or `plays`. For the most recently *played* albums use `recent`.

### `GET /api/library/random-album?scope=&device_id=`

`{ "data": AlbumItem }` — one random album with at least one visible track in the scope (artwork with `colors`, for a "surprise me" button). `scope` is a library id (`dlna`, `spotify`, …), `local`, `streaming` or `all`, and `client` hides sources, exactly as on the other browse endpoints; an unknown `scope` is a `422`, and an empty library (nothing to pick) a `404` (`{ "message": "No albums in this library." }`). With `device_id` an album that device can play (the `playable` rule of the album detail: some visible track has a DLNA stream the device can play or a Spotify URI while Spotify is usable on it) is preferred; when none is playable, any album is returned. The pick is a random offset into the matching albums (one count, one single-row query), so it stays cheap on a large library.

### `GET /api/library/artists/{id}`

`{ "id", "name", "favorite", "genres": [ "Rock", … ], "details": ArtistDetails, "albums": [ AlbumItem, … ] }` — albums newest year first (unknown year last), then by name.

**ArtistDetails** — `{ "type": "group"|"person"|…|null, "country": "GB"|null, "area": "London"|null, "begin_date": "1994"|null, "end_date": null, "bio": "…"|null, "wikipedia_url": "…"|null, "links": { "official": "…", "discogs": "…", … } }`. `bio` is the Wikipedia summary, else the Last.fm bio. Dates are MusicBrainz partial dates (`1994`, `1994-05`, `1994-05-12`). `links` keys that may occur: `official`, `wikidata`, `wikipedia`, `discogs`, `allmusic`, `lastfm`, `bandcamp`, `songkick`, `youtube`, `twitter`, `instagram`, `facebook`, `spotify`, `apple_music`, `deezer`, `tidal`. Besides: `"images": { "thumb": "https://…", "fanart": "…", "logo": "…", "banner": "…" }` (TheAudioDB, any key may be absent; remote originals), `"mood"`, `"style"`, `"tags": ["Shoegaze", …]` (Last.fm), `"listeners"`, `"playcount"` (Last.fm, integers). Every field is filled in as enrichment reaches the artist (see `docs/architecture/metadata-enrichment.md`), so all may be `null`/empty.

### `GET /api/library/albums/{id}?device_id=`

```json
{
  "id": 12,
  "name": "Absolution",
  "artist": { "id": 1, "name": "Muse" },
  "year": 2003,
  "artwork": { "hash": "…", "proxy_120": "…", "proxy_320": "…", "colors": ["#…"], "safe_colors": ["#…"] },
  "favorite": false,
  "sources": ["files", "dlna", "spotify"],
  "genres": ["Alternative Rock"],
  "details": {
    "label": "Mushroom", "catalog_number": "MUSH-1", "release_type": "album", "secondary_types": ["live"],
    "release_date": "2003-09-15", "country": "GB", "track_count": 14, "disc_count": 1,
    "summary": "…", "wikipedia_url": "…", "format": "Vinyl, LP, Album", "mood": "Dreamy", "style": "Rock/Pop", "theme": null,
    "rating": 8.7, "tags": ["Alternative Rock"], "credits": { "producer": ["Rich Costey"] }, "discogs_url": "…",
    "listeners": 1200, "playcount": 99000
  },
  "playable": true,
  "tracks": [ { "id": 34, "name": "Intro", "duration": 213, "playable": true, "details": TrackDetails } ]
}
```

`sources` lists where the album's visible tracks come from: `files`, `dlna` and/or `spotify`, in that order (a track merged from both counts for both; `App\Domain\Library\LibrarySources::ofTracks`). Playlists (`GET /api/library/playlists/{id}`) have the same field.

**TrackDetails** — `{ "genres": [], "quality": "FLAC · 16-bit / 44.1 kHz · 1411 kbps · stereo"|null, "credits": { "composer": ["…"], "instrument": ["Name (guitar)"] }, "isrc": null, "explicit": true|false|null, "popularity": 67|null, "listeners": null, "playcount": null, "analysis": TrackAnalysis|null }`. `quality` is what a DLNA server reported; `credits` are MusicBrainz credits grouped by role (an empty object when none); `popularity` is Spotify's 0–100; `listeners`/`playcount` are Last.fm's.

**TrackAnalysis** — what the server computed from the track's own audio file, `null` until the file is analysed (own files only; see `docs/architecture/audio-analysis.md`): `{ "bpm": 124.0|null, "key": "A"|null, "mode": "minor"|null, "camelot": "8A"|null, "loudness": -9.2|null, "loudness_range": 6.4|null, "true_peak": -0.5|null, "plr": 8.7|null, "replaygain_track_gain": -3.1|null, "replaygain_album_gain": null, "danceability": 0.8|null, "arousal": null, "valence": null, "instrumental": 0.9|null, "mood": ["relaxed"], "recording_mbid": "…"|null, "spectral_cutoff_hz": 16500|null, "lossless_suspect": 0.95|null, "measured_bit_depth": 24|null, "clipping": false|null, "mono": false|null, "phase_issue": false|null, "lead_silence_ms": 0|null, "trail_silence_ms": 0|null, "decode_warnings": [] }`. `loudness` is integrated EBU R128 loudness in LUFS, `true_peak` in dBFS, the gains in dB; `key` uses sharps (`C`…`B`); `camelot` is the same key on the Camelot wheel (`1A`…`12B`, for harmonic mixing), `plr` the peak-to-loudness ratio in dB (`true_peak - loudness`: low is heavily compressed); `danceability`, `arousal`, `valence` and `instrumental` are fractions 0–1; `mood` lists the classifier moods. The quality fields come from the `quality` stage (ffmpeg only, so also on a Pi): `spectral_cutoff_hz` is where the spectrum falls off a cliff (`null` when it does not), `lossless_suspect` is 0–1 for a lossless file (how likely it is a transcode or an upsampled hi-res file; `null` for lossy files; treat it as "suspected", never as proof), `measured_bit_depth` the bits a lossless file's samples really use, `clipping` flat repeated peaks, `mono` identical channels, `phase_issue` channels largely out of phase, and `decode_warnings` what the decoder complained about (empty list when nothing). What clients should show, when, and in which words: [sound-and-quality.md](sound-and-quality.md). Fields are `null` while the stage that computes them has not run (BPM, key, danceability, mood need the Essentia sidecar; arousal, valence, instrumental and mood its ML build).

Tracks are in best-effort album order (by id — there is no track number column). `duration` is seconds or `null`. A track is `playable` when the server has a stream for it: a DLNA URL, or a Spotify URI. With the optional `device_id`, `playable` is for that device: DLNA tracks need a device with a DLNA library driver, Spotify tracks a device that can play Spotify (below). The album is `playable` when any track is.

### `GET /api/library/genres`

`{ "data": [ { "slug": "alternative-rock", "name": "Alternative Rock", "artist_count": 12, "album_count": 30, "colors": [ "#2a4d8f", "#c7776b" ] }, … ] }` — genres with at least one artist or album, most artists first. Genres are canonical: spellings of one genre ("hip hop", "Hip-Hop") are one entry.

`colors` is `["#rrggbb", …]`, at most 3, the genre's dominant colour first, derived from the cached artwork palettes (`colors` of the cover's cache entry, one bulk cache read, never recomputed) of the albums `album_count` counts (same `scope` and client-hidden filtering). Rule: sample at most 200 albums per genre (most played first, then lowest id); per album take the first 2 palette entries; quantise every channel in steps of 32 (`floor(c/32)`) and group by bucket; count albums per bucket (an album counts once per bucket); the bucket's colour is its most frequent exact hex (ties: lower hex). A bucket is *vivid* when its colour has HSV saturation >= 0.25 and value between 0.2 and 0.95; vivid buckets rank first by album count, then the rest by album count (ties: order of first appearance), top 3 returned. Covers not processed yet add nothing; a genre without any gives `[]` (never null or absent). Computed per genre + scope + client-hidden sources and cached for 1 hour, so a new album shows within an hour.

### `GET /api/library/genres/{slug}`

`{ "slug", "name", "colors": [ "#rrggbb", … ], "artists": [ ArtistItem, … ], "albums": [ AlbumItem, … ] }` — up to 100 of each: artists with albums alphabetically ("The " ignored), albums newest year first. `colors` as in the list. Unknown slug: `404`.

### `GET /api/library/playlists?cursor=`

`{ "data": [ PlaylistItem, … ], "next_cursor": "…"|null }` — playlists with at least one track, 50 per page: the most recently played first, then those never played, by name (case-insensitive). "Played" means started from the server — `play-playlist` or the web play button — which sets `playlists.last_played_at`; starting a playlist in the Spotify app doesn't count. Paged with an opaque cursor like the artists. In the Local scope (`scope=dlna`, `scope=local`, or no `scope` while Local is the leading library) Spotify playlists with enough local copies are listed too, flagged `external`: see [Playlists of another library, played locally](#playlists-of-another-library-played-locally). Every other scope lists exactly the playlists it did before.

### `GET /api/library/playlists/{id}?device_id=&library=`

```json
{
  "id": 3,
  "name": "Discover Weekly",
  "owner": "Spotify",
  "last_played_at": "2026-10-01T12:00:00+00:00",
  "artwork": { "hash": "…", "proxy_120": "…", "proxy_320": "…", "colors": ["#…"], "safe_colors": ["#…"] },
  "mode": "library",
  "mode_library": "spotify",
  "sources": ["spotify"],
  "track_count": 42,
  "local_track_count": 30,
  "local_coverage": 0.71,
  "smart": false,
  "rules": null,
  "rules_summary": null,
  "playable": true,
  "tracks": [ { "id": 34, "name": "Intro", "artist_name": "Muse", "duration": 213, "artwork": { "hash": "…", "proxy_120": "…", "proxy_320": "…", "colors": ["#…"], "safe_colors": ["#…"] }, "playable": true } ]
}
```

The first 200 tracks in playlist order. `mode`, `mode_library`, `track_count`, `local_track_count` and `local_coverage` are explained in [Playlists of another library, played locally](#playlists-of-another-library-played-locally) (`track_count` is the number of listed tracks when there are fewer than 200, else the real total; a playlist of a library (Spotify) lists every track visible in that library, not just those the default Local scope shows, still minus the sources the client hides; the two local fields are `null` for local and smart playlists). `artist_name` and `duration` (seconds) can be `null`. `playable` works as for albums: a stream exists for the track (DLNA URL or Spotify URI), or, with `device_id`, that device can play it; the playlist is `playable` when any listed track is. `last_played_at` is when it was last started from the server (`null` if never), `sources` the libraries its visible tracks come from (as for albums).

**Playlists of a library.** A playlist that belongs to a library (a Spotify playlist: `source` `spotify` / `external_id` `spotify:playlist:…`; `LibraryPlayback::playlistLibrary`) is that library's and nothing else: `sources` is just `["spotify"]` even when its tracks also exist in DLNA (merged copies), and it plays only through that library. With `device_id`, `playable` (playlist and tracks) is true only when the device can play the library (`LibrarySources::playableOn`, as `playable` in `GET /api/library/libraries`: Spotify connected and the Spotify device or a speaker mapped to a Spotify Connect name) and, for a track, it exists in the library; a Spotify playlist is not `playable` on a DLNA-only device. Without `device_id`, tracks are `playable` when they exist in the playlist's library. Local and smart playlists have no library of their own and keep the track-derived `sources` and per-track `playable` described above. The list (`PlaylistItem`) carries neither field; in `recent-items` such a playlist's `library` is its own (`spotify`).

Each track's `artwork` is the cover of the track's album, the same small object as album items (`null` when the track has no album or the cover isn't processed yet: show the placeholder). Covers of the whole page are resolved in one cache read.

**Smart playlists** (`docs/architecture/smart-playlists.md`): `"smart": true`, and `rules` and `rules_summary` are filled; for other playlists `smart` is `false` and both are `null`.

```json
"smart": true,
"rules": {
  "match": "all",
  "rules": [
    { "field": "genre", "operator": "is", "value": "12", "text": "Genre is Rock" },
    { "field": "plays", "operator": "gte", "value": 3, "text": "Times played at least 3" }
  ],
  "sort": "most_played",
  "limit": 50
},
"rules_summary": "Genre is Rock and Times played at least 3, up to 50 tracks"
```

`rules` is the stored definition (`match` `all`|`any`, `sort`, `limit`; unknown fields dropped), each rule with its readable phrase in `text`. `rules_summary` is one English sentence: the rule phrases joined with "and" (`match: all`) or "or" (`any`), then ", up to N tracks"; no rules reads "Every track in the library, …". Built by `SmartPlaylistDescriber` from the `SmartFields` labels.

### Playlist artwork

Playlist covers are generated, like Spotify's: a **2×2 mosaic of 4 album covers** from the playlist — those of the 4 albums with the most tracks in it (ties: the album that comes first in the playlist), left to right, top to bottom; albums sharing a cover count once. With 1–3 distinct covers, the cover is the first of those albums' cover (its `hash` is the album's); with no album covers, the playlist's own image (e.g. Spotify's), else `null`.

The mosaic is used **even when the playlist has its own image**, so all playlists look alike on the clients whatever their source (Spotify's own images are often a mosaic or a personalised banner anyway). A composite is addressed by the pseudo URL `remoment:playlist/v1/{md5 of the 4 cover URLs, newline-joined, in tile order}` and goes through the normal artwork pipeline (`ProcessArtwork`: the same 512/320/120 squares, `proxy_bg`/`proxy_bg_320x480`, colors, baseline JPEGs) — so its `hash` is `md5` of that URL, and changes exactly when the 4 chosen covers change. Like album covers it is `null` until processed (queued at most once an hour); `artwork:prerender` and `artwork:backfill` (both daily) queue missing ones, and processed composites are in the client pre-cache list as `kind: "playlist"` items (`docs/api/client-devices.md`). Code: `App\Domain\Artwork\PlaylistArtwork` (choice, URL), `PlaylistCompositeRenderer` (drawing: processed covers are read from their 512 proxy, others downloaded directly, so a composite doesn't wait for its covers' own jobs).

### `GET /api/library/libraries[?client={api_token}][&device_id={id}]`

A **library** is a music collection: Local (own files, id `files`), DLNA and Spotify, later Deezer and Tidal. (A *source*, in the device APIs, is an input of a device: never the same thing.) Libraries cannot be played combined, so there is no "all" entry. Registered in `App\Domain\Library\LibrarySources::LIBRARIES`: adding one there makes it appear here, accepted as a `scope` and hideable per client.

```
{ "data": [ Library, … ] }
Library = { id, name, kind, album_count, artist_count, playlist_count, artwork, playable? }
  id        "files" | "dlna" | "spotify" | … (also a valid `scope`)
  name      "Local" | "DLNA" | "Spotify" | …
  kind      "local" | "streaming"
  *_count   what the library has for this client (a track merged from DLNA and Spotify counts in both)
  artwork   a representative cover (the library's most recently played album with a cover, else its newest), the small
            LibraryArtwork object; null until processed or without covers
  playable  only with `?device_id=`: whether that device can play this library, boolean. Absent without `device_id`
            ("unknown"). A library that is not playable stays listed: it can still be browsed
```

`playable` uses the rules of "Library playback" below, per library: `dlna` needs a device whose driver implements `LibraryPlaybackInterface`; `spotify` needs Spotify connected and the device to be the Spotify virtual device or mapped to a Spotify Connect name. Each library declares its check as `device` in `LibrarySources::LIBRARIES` (the `LibraryPlayback::canPlay…` methods the play endpoints use), so a future library adds its rule in that one place. An unknown `device_id` is `422` (like the other `device_id` query parameters).

Only libraries with albums or playlists that are not hidden for the client are listed (`?client=`, see below; unknown token `404`), local libraries first, then streaming ones (`LibrarySources::forDisplay()`).

### `GET /api/library/recent-items?limit=30[&client={api_token}]`

Recently played albums, playlists and radio stations in one list, newest first. `limit` 1–100, default 30.

```
{ "data": [ { type, library, played_at, album, playlist, station }, … ] }
  type       "album" | "playlist" | "radio"
  library    a library id, or "radio" for a station
  played_at  ISO 8601
  album      AlbumItem | null     } exactly one is set, matching `type`
  playlist   PlaylistItem | null  }
  station    RadioStation | null  }  (the shape of GET /api/devices/{id}/radio)
```

- Albums: their latest play (as in `recent`). Playlists: `playlists.last_played_at` (never-played ones are not listed). Stations: `radio_stations.last_played_at`, set whenever a station is started through the server (the API, the web UI or the device card); a station played elsewhere is not known.
- `library` of an **album**: the library of the track it was last played from (`plays` → `tracks.source`), if the client doesn't hide it; otherwise its leading library: the leading library (`/settings/library`) if the album is available from it, else the first library of `LibrarySources::LIBRARIES` it is available from. A **playlist** has no per-library play record: its own `source` if that is a library (a Spotify playlist is `spotify`), otherwise (local and smart playlists) the same leading-library rule over its tracks.
- Radio is never hidden unless `radio` is in the client's hidden sources. Albums and playlists follow the client's hidden sources too; `scope` does not apply (every library is included, `library` says which).

### `GET /api/library/recent?limit=30`

`{ "data": [ AlbumItem, … ] }` — the most recently played distinct albums, newest first (`LibraryArtwork::lastPlayedPerAlbum()`, the same recency as the pre-cache list). `limit` 1–100, default 30.

## Hiding sources per client

An admin can hide sources from a client at `/settings/clients` (edit → *Hide from library*): `files`, `dlna`, `spotify` and `radio` (`App\Domain\Library\LibrarySources::ALL`; a future source is added there). The setting is `clients.hidden_sources` (JSON array).

A client applies it by adding its API token as `?client={api_token}` to the browse endpoints (`/api/library/libraries`, `recent-items`, `artists`, `artists/{id}`, `albums/{id}`, `genres`, `genres/{slug}`, `playlists`, `playlists/{id}`, `recent`, `favorites`) and to `GET /api/devices/{id}/radio`. Without the parameter no client preference applies; an unknown token is `404`.

**Library scope.** The browse endpoints also take `?scope=` (`422` for anything else): a **library id** from `GET /api/library/libraries` (`files`, `dlna`, `spotify`, later `deezer`, `tidal`) to show only that library, or the older `local` (the libraries of kind `local`: your own files), `streaming` (kind `streaming`: DLNA, Spotify, later Deezer/Tidal) and `all` (every library combined), which keep working unchanged. A track available from two libraries shows in either. The playlist list, favorites, recent, genres, albums, artists and search all take it; `playlists?scope=all` lists the playlists of every library, last-played first, smart playlists included. Without `scope` the default is the leading library: the own files when indexed, else DLNA when it has imported tracks, otherwise Spotify (admin setting `/settings/library`: Automatic, Local files, DLNA, Spotify or Everything, which defaults to `all`). `GET /api/clients/{api_token}/artwork` always uses the default. Nothing is deleted, the scope only filters. `GET /api/clients/{api_token}/artwork` applies it from its path.

- A track is available from its own `source` and from the sources of its `dlna_url` (`dlna:{server}`, own files: `files`) and `external_id` metadata, so a track merged from DLNA and Spotify. It is hidden only when **all** of those are hidden.
- Albums, artists and playlists with no visible track are left out; counts (`album_count`, `track_count`, genre counts) and album/playlist `tracks` only count visible tracks.
- `radio` empties the `/radio` station list (`{ "stations": [] }`).
- Playing is not blocked: the filter is for browsing, so playing a hidden id still works.
- The playlist cover list in the artwork pre-cache is not filtered.

## Search

```
GET /api/library/search?q=hyster[&client={api_token}]
  → { "artists": [ ArtistItem ], "albums": [ AlbumItem ], "tracks": [ SearchTrack ] }
SearchTrack = { id, name, artist_name, album_id, album_name, duration, artwork }
```

Case-insensitive substring match on the artist, album and track name; `q` is 2–100 characters (`422` otherwise). At most 10 artists, 15 albums and 20 tracks, each sorted by name. Tracks without an album are left out: play one with `play-album` (`album_id`, `start_track_id` = the track's `id`). `?client=` hides sources as in the other browse endpoints. Playlists are not searched.

## Favorites

Household-wide (there are no user accounts): `albums.favorited_at` / `artists.favorited_at`, `null` when not a favorite.

```
PUT /api/library/albums/{id}/favorite    body: { "favorite": true }   → { "favorite": true }
PUT /api/library/artists/{id}/favorite   body: { "favorite": true }   → { "favorite": true }
GET /api/library/favorites               → { "albums": [ AlbumItem ], "artists": [ ArtistItem ] }
```

Favorites are listed most recently favorited first; favoriting an item again keeps its original time. The web album and artist pages show a heart that toggles the same flag (`POST /albums/{id}/favorite`, `POST /artists/{id}/favorite`).

## Play on a device

```
POST /api/devices/{id}/library/play-album     body: { "album_id": 12, "start_track_id": 34, "shuffle": false }    → { "status": "ok", "album": "Absolution" }
POST /api/devices/{id}/library/play-artist    body: { "artist_id": 5, "shuffle": true }                           → { "status": "ok", "artist": "Muse" }
POST /api/devices/{id}/library/play-playlist  body: { "playlist_id": 3, "start_track_id": 12, "shuffle": false, "library": "files" } → { "status": "ok", "playlist": "Discover Weekly", "mode": "library" }   (local mode adds "queued", "skipped"; see below)
```

`library` (play-playlist only, optional) is the library the playlist was browsed in; it picks the playback mode (see [Playlists of another library, played locally](#playlists-of-another-library-played-locally)). `start_track_id` (optional) must be a track of that album (or playlist); playback starts there and continues to the end of the album (playlist, in playlist order). `shuffle` (optional, default `false`) shuffles the order (after the start track, if given). An artist plays all its library tracks, grouped by album.

Two paths, tried in this order:

1. **DLNA** — when the device's driver implements `LibraryPlaybackInterface` (B&O ASE, Sonos, Mozart) and at least one track has a DLNA URL (`dlna_url` metadata from a DLNA scan). The tracks are queued on the device; tracks without a URL are skipped.
2. **Spotify** — when Spotify is connected, the device is the Spotify virtual device or a local device mapped to a Spotify Connect name (`/settings/spotify-connect`, the mapping the Spotify listener routes by), and at least one track has a Spotify URI (`external_id` `spotify:track:…`: tracks from the Spotify library import or from playing Spotify — or kept as `external_id` metadata with source `spotify` on a track that is also on DLNA). The server looks up the Connect device by its mapped name in `GET /v1/me/player/devices` (the Spotify device plays on whatever Connect device is active) and calls `PUT /v1/me/player/play`:
   - an **album** plays as its Spotify album context — the full album, also tracks not in the library — offset at the start track (or a random library track when shuffling). The album URI is looked up once from one of its tracks (`GET /v1/tracks/{id}`) and stored as album metadata `spotify_album_uri`. If that fails, the album's library tracks are played as a list of URIs;
   - an **artist** plays its library tracks as a list of URIs (at most 100);
   - a **Spotify playlist** (`external_id` `spotify:playlist:…`) plays as its Spotify playlist context, offset at the start track (or a random track when shuffling); any other playlist plays its tracks like an album (DLNA first, then Spotify track URIs). A Spotify playlist is never played as the local DLNA copies of its tracks: on a device that can't play Spotify, `play-playlist` answers `422 not_playable`;
   - then shuffle is set to `shuffle` on that device (best effort).

The device then reports the playback through its listener as usual (for a mapped speaker via Spotify routing, see CLAUDE.md).

Errors:

| Status | Body | When |
|---|---|---|
| `422` | `{ "error": "not_playable", "message": "…" }` | Neither path works for this device and album/artist/playlist (no DLNA driver or DLNA tracks; not Spotify-capable or no Spotify tracks) |
| `422` | `{ "error": "unsupported", … }` | play-playlist only: the device has no `library_playback` at all (kept from before) |
| `422` | Laravel validation `{ "message", "errors" }` | Unknown `album_id`/`artist_id`/`playlist_id`, `start_track_id` not on the album/playlist |
| `503` | `{ "error": "unreachable", … }` | The device is unreachable |
| `502` | `{ "error": "driver_error", "message": "…" }` | The device or Spotify refused or didn't respond, or Spotify doesn't currently list the mapped Connect speaker (it may be asleep) |

The same paths also serve the older `POST /api/devices/{id}/library/play` (`track_id`), which falls back to Spotify for a Spotify track; its error shapes are unchanged (`no_dlna_url` on DLNA devices). `play-playlist` with only `playlist_id` still plays the whole playlist in order.

### Playlists of another library, played locally

A playlist belongs to a **library** (`spotify` for a synced Spotify playlist; local and smart playlists belong to none). A **source** is something else (an input of one device) and plays no part here. Libraries are never played combined, so a playlist plays in exactly one of two **modes**, decided by the server:

| Mode | What plays | Needs a device that can play |
|---|---|---|
| `library` | The playlist's own library plays it: a Spotify playlist is loaded as a Spotify context and Spotify Connect handles playback. Local/smart playlists play their tracks as always (Local first, then Spotify URIs). | the playlist's library (`playable` in `GET /api/library/libraries?device_id=`) |
| `local` | The server queues the playlist's tracks that have a playable copy in the **Local** library (`files`), in playlist order, and **skips** the rest. | Local |

**Which mode:** it follows from where the playlist was opened. The client passes the id of the library it was browsing as `library` (the same ids as `scope`: `dlna`, `spotify`, …), the server decides and validates:

| Playlist | `library` absent | `library` = its own library | `library=files` | any other library |
|---|---|---|---|---|
| Spotify playlist | `library` mode, `mode_library` `spotify` | `library` mode, `spotify` | **`local` mode**, `files` | `422` |
| Local or smart playlist | `library` mode, `mode_library` `null` | n/a | `library` mode, `files` | `422` |

So: a playlist opened from the Spotify library plays through Spotify; the same playlist opened from the Local library plays the local copies. A client does not decide anything: it shows the response's `mode`, and sends the same `library` to play. `422` here is a Laravel validation error on `library`.

**Coverage.** For a playlist of another library the server counts how many of its tracks have a playable Local copy (a `dlna_url` from the own files; a track counts once per place in the playlist):

- `track_count`: all tracks of the playlist,
- `local_track_count`: those with a local copy,
- `local_coverage`: `local_track_count / track_count`, 0 to 1, rounded to 2 decimals (`0.71`); `null` without tracks.

For local/smart playlists (and playlists of the Local library) the two local fields are `null`. Counted for a whole page with one aggregate query (`App\Domain\Library\PlaylistCoverage`).

**List.** `GET /api/library/playlists?scope=files` (or `local`) lists the Local playlists and, additionally, the playlists of another library with `local_coverage >= 0.4` (`PlaylistCoverage::MIN_COVERAGE`, the one place the threshold lives; it is compared after rounding, so `0.40` is in, `0.39` is out). Ordering and paging are as ever (last played first, then name; one cursor over the combined list). `scope=all` and the other scopes list each playlist once, as itself, never external. Items:

```json
{ "id": 7, "name": "Mix", "track_count": 20, "owner": null, "last_played_at": null, "artwork": null,
  "library": null, "external": false, "local_track_count": null, "local_coverage": null }
{ "id": 9, "name": "Discover Weekly", "track_count": 30, "owner": "Spotify", "last_played_at": null, "artwork": null,
  "library": "spotify", "external": true, "local_track_count": 18, "local_coverage": 0.6 }
```

`external` is `true` only in the Local scope, for a playlist that belongs to another library; open it with `library=files` (what the client is browsing) so it gets local mode. Show the coverage ("18 of 30 tracks in Local") and, for tracks that are missing, mark them. A client that hides the playlist's library (`?client=`) does not get it as external either.

**Detail.** `GET /api/library/playlists/{id}?device_id=&library=files` on a Spotify playlist:

```json
{
  "id": 9, "name": "Discover Weekly", "owner": "Spotify", "last_played_at": null, "artwork": { … },
  "mode": "local", "mode_library": "files", "sources": ["files"],
  "track_count": 30, "local_track_count": 18, "local_coverage": 0.6,
  "smart": false, "rules": null, "rules_summary": null,
  "playable": true,
  "tracks": [
    { "id": 34, "name": "Intro", "artist_name": "Muse", "duration": 213, "artwork": { … }, "playable": true,  "missing_locally": false },
    { "id": 35, "name": "Only on Spotify", "artist_name": "Muse", "duration": 180, "artwork": null, "playable": false, "missing_locally": true }
  ]
}
```

- `mode_library` is the library playback goes through.
- In library mode a playlist of a library (Spotify) lists all its tracks in playlist order, whatever `scope` says (the client's own hidden sources still apply); local and smart playlists follow `scope`.
- In local mode **all** tracks are listed (the `scope` filter does not hide the missing ones); `playable` means "has a local copy playable on `device_id`" (false for everything when the device cannot play Local), `missing_locally` is `true` for tracks without a local copy. Both keys `playable` and `missing_locally` are only present in local mode as a pair; in library mode a track has just `playable`.
- `playable` of the playlist: in local mode the device can play Local and at least one track has a local copy.
- Without `library` (or `library=spotify`) the same Spotify playlist answers `"mode": "library"`, `"mode_library": "spotify"`, `"sources": ["spotify"]` and the playability described under *Playlists of a library*, exactly as before.

**Play.** `POST /api/devices/{id}/library/play-playlist` takes the same optional `library` in its body (`{ "playlist_id": 9, "library": "files", "start_track_id": 34, "shuffle": false }`); the mode is decided like for the detail.

```json
{ "status": "ok", "playlist": "Discover Weekly", "queued": 18, "skipped": 12, "mode": "local" }
{ "status": "ok", "playlist": "Discover Weekly", "mode": "library" }
```

Local mode queues the tracks with a local copy in playlist order (from `start_track_id` onwards when given, shuffled when asked) and reports `queued` (what was queued) and `skipped` (playlist tracks without a local copy); `start_track_id` must be a track with a local copy. Library mode has no counts (Spotify plays the playlist). Failures: `422 { "error": "not_playable", "message": "…" }` when the device cannot play the mode's library (the message names the library, e.g. "…can only be played from the Local library here, which this device can't play." or "…plays through the Spotify library, which this device can't play."), or when local mode would queue nothing; `422` validation on `library` for a library that makes no sense for the playlist. `last_played_at` is set on success only; nothing is recorded or started on a `422`.

Client guidance: pass the library you are browsing in (`library`) to `GET /playlists/{id}` and to `play-playlist`; disable or hide Play when `playable` is false; for `external` playlists show the coverage and the missing tracks greyed out. Do not compute modes or coverage on the client.

### Capability

A device lists `library_playback` in `capabilities` when either path exists for it: a DLNA library driver, or (Spotify connected and) being the Spotify device or mapped to a Spotify Connect name (`App\Domain\Device\DeviceCapabilities`). It says nothing about a particular album or playlist — use its `playable` with `device_id` for that.


### Jumping to a letter

`GET /api/library/artists?letter=M` starts the list at the first artist sorting at or after that letter (a leading "The " is ignored, like the sort). `#` is the start of the list. `next_cursor` continues from there. Used by the clients' A-Z bar.

`GET /api/library/albums?letter=M` does the same for albums, following the active sort: with `sort=name` (default) the album name, case-insensitive (a leading "The " is **not** ignored for album names, as in that sort), with `sort=artist` the artist name ("The " ignored). With `year`, `added` and `plays` `letter` has no effect. Names starting with a digit or symbol sort before A, so `A` skips them and `#` is the start. `letter` is one character `A-Z`/`a-z`/`#`, anything else is a `422`; it is ignored when a `cursor` is given. The jump respects `scope` and the client's hidden sources.


**Artist fanart** — `details.fanart` is `{ hash, proxy_120, proxy_320, proxy_512, proxy_bg, proxy_bg_320x480, proxy_bg_480x480, colors, safe_colors }` (the TheAudioDB fanart run through the artwork pipeline; root-relative `/storage/…` paths) or `null` until processed (queued, at most once an hour) or when the artist has none. The `proxy_bg*` keys are blurred, darkened backdrops for a screen of that size. The web artist page uses `proxy_bg` as its hero background.

`details.gallery` is the same for every wide photo TheAudioDB has (fanart 1–4 and the wide thumb): a list of those objects, only the processed ones (the rest are queued). The web artist page shows them as a strip under the hero, each linking to the original.
